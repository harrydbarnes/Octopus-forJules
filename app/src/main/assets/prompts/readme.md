You are tasked with creating or fully rewriting the README.md for this project. The goal is a README that is genuinely useful, welcoming, and easy to navigate — for first-time visitors, contributors, and people who want to self-host. You can have fun with it: use relevant emojis as visual anchors throughout, but keep it professional and clear.

**Study the codebase thoroughly before writing a single line.** Understand what the project is, what it does, how it is built, what technologies it uses, and how someone would run or deploy it. Do not make anything up — every claim in the README must be accurate and grounded in what actually exists in the code.

**The README must include the following sections, in this order:**

---

### 1. Header
- Project name as the H1 title with a fitting emoji.
- A short, punchy one-liner describing what the project is.
- Badges where relevant (build status, licence, latest release, platform support, etc.) — only include badges that can actually be populated correctly from this repo.

### 2. What Is This?
- A clear, jargon-free explanation of what this project is and what problem it solves.
- Who it is for (developers, end users, businesses, hobbyists, etc.).
- Keep this concise — two to four sentences maximum.

### 3. Features ✨
- A bullet list of the key features and capabilities.
- Use emojis as bullet markers to keep it visually engaging.
- Be specific — avoid vague claims like "fast" or "easy to use" unless there is concrete evidence in the code.

### 4. Built With 🛠️
- List every significant open source library, framework, or tool used in the project.
- For each one, include: the name (linked to its homepage or repo), what version is being used, and a brief note on what it is used for in this project specifically.
- Group by category if it makes sense (e.g. Frontend, Backend, Build Tools, Testing).

### 5. Getting Started 🚀
- Step-by-step instructions for getting the project running locally from a fresh clone.
- Include prerequisites (runtime versions, required tools, environment variables, etc.).
- Use numbered steps and code blocks for every command.
- Cover both common platforms where relevant (e.g. macOS/Linux and Windows differences).

### 6. How to Use It 📖
- A practical guide to using the application or library once it is running.
- Include screenshots, GIFs, or example code snippets where they would genuinely help.
- If the project has multiple distinct use cases, cover each one.

### 7. Self-Hosting Instructions 🏠
- Full, standalone instructions for deploying and running this project on your own infrastructure.
- Include: environment variable configuration, any required services or databases, reverse proxy setup if relevant, and how to keep it updated.
- Cover Docker-based deployment if the project supports it (or note if it does not).
- Be explicit about any security considerations for production deployments (e.g. secrets management, exposed ports, authentication).

### 8. Configuration ⚙️ (if applicable)
- Document all available configuration options, environment variables, or config files.
- Use a table format with columns: Variable / Option, Description, Default Value, Required.

### 9. Contributing 🤝
- A short, welcoming paragraph inviting contributions.
- Link to CONTRIBUTING.md if it exists, or include brief guidelines inline.
- Note the branching strategy or PR process if it is evident from the repo.

### 10. Licence 📄
- State the licence clearly and link to the LICENSE file.

---

**Tone and Style Guidelines:**
- Write in clear, plain English. Avoid overly technical jargon in the introductory sections.
- Use emojis as section anchors and occasional emphasis — not scattered randomly throughout every sentence.
- Use proper Markdown formatting throughout: headers, code blocks with language hints, tables, and blockquotes where appropriate.
- Every code block must be accurate and copy-pasteable — test any commands you include against the actual project structure.
- Do not pad the README with filler content. Every sentence should earn its place.
- If a section is genuinely not applicable to this project, omit it rather than leaving a placeholder or writing something vague.
